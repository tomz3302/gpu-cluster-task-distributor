Measuring Performance
• Program execution time is the measure of computer performance:– Also known as response time, elapsed time, or latency– It is the time between the start and completion of a task– It is the wall-clock time– Measured in seconds per program– The computer that performs the same amount of work in the least time 
is the fastest– Important for individual computer users– Focus of embedded or desktop computers
• Throughput or bandwidth could also be used to measure performance:– It is the total amount of work done in a given time– Important for datacenter managers– Focus of servers
• Decreasing execution time almost always improves throughput
• Changing either execution time or throughput often affects the other

Defining Time
• Program execution time can be defined in different ways:– Execution (response or elapsed) time
• the total time required for the computer to complete a task
• the time between the start and completion of a task
• counts everything: disk accesses, memory accesses, I/O activities, 
OS overhead, CPU execution time, time spent in other programs, 
etc.
• it is the time experienced by the user
• not useful for time sharing comparisons
• execution time on unloaded system expresses system performance– CPU execution time (simply CPU time)
• the actual time the CPU spends computing a task’s lines of code
• does not include time spent waiting for I/O activities or running 
other programs

Defining Time (cont.)
• CPU time can be further divided into:– User CPU time
• the CPU time spent in the program itself
• expresses CPU performance
• our focus for assessing performance– System CPU time
• the CPU time spent in the OS performing tasks on behalf of 
the program
• It is hard to differentiate between user CPU time and system CPU 
time since:– it is often hard to assign responsibility for OS activities to one 
user program rather than another– functionalities differ among OSs

• Computers are constructed using clocks running at constant rates
• Clock cycles indicate when events take place in the hardware (one 
abstraction)
time
• Instead of reporting execution time in seconds, we often use cycles
• Clock cycles: ticks, clock ticks, clock periods, clocks, cycles
• We can count the number of CPU clock cycles for a program
• Clock cycle time/period (T):– time for a complete clock cycle– time between ticks– seconds per cycle
• Clock rate/frequency (R):– the inverse of the clock period, i.e.,– cycles per second

Static and Dynamic Instruction Count
• Static instruction count is the number of instructions 
the program has
• Dynamic instruction count is the actual number of 
instructions executed by the CPU for a specific program 
execution– We usually use dynamic instruction count as if, for 
example, you have a loop in your program then some 
instructions get executed more than once– Also, in the presence of branches, some instructions 
may not be executed at all

• IPS: Instructions Per Second (instruction execution rate) •MIPS: Million Instructions Per Second
• Problems with using MIPS as a measure for comparing computers:–MIPS specifies the instruction execution rate but does not take into 
account instruction capabilities. We cannot use it to compare computers 
with different ISAs, since instruction counts will certainly differ–MIPS varies between programs on the same computer; thus a computer 
cannot have a single MIPS rating for all programs–MIPS can vary inversely/independently with performance, for example:
• Since it generally takes more clock cycles per floating-point 
instructions than per integer instructions, floating-point programs 
using the optional hardware instead of software floating-point 
routines take less time but have a lower MIPS rating
• Software floating-point routines execute simpler instructions, 
resulting in higher MIPS rating, but they execute so many more 
causing overall execution time to be longer • Same architecture computers can be compared using MIPS

Amdahl's Law in Computing (cont.)
• Corollary: make the common case fast– The opportunity for improvement is affected by how much time 
the event consumes. Thus, making the common case fast will 
tend to enhance performance better than optimizing the rare case– This is a common theme in hardware design– The common case is often simpler than the rare case and hence 
is often easier to enhance!
• Amdahl’s law tells how much an improvement will enhance 
performance and how to distribute resources to improve 
cost/performance– The goal is to spend resources proportional to where time is spent
• Amdahl’s law can also be used to compare two design alternatives
• Common mistake in applying Amdahl’s law is to confuse– fraction of time converted to use an improvement, and– fraction of time after improvement is in use

The Power Wall (cont.)
• Clock rate and power increased rapidly for decades, then flattened off 
lately
• The reason they grew together is that they are correlated
• The reason for their recent slowing is that we have run into the 
practical power limit for cooling commodity microprocessors
• Pentium 4 made a big jump in clock rate and power but less in 
performance
• Pentium 4 thermal problems led to the abandonment of the Pentium 
4 line
• Core 2 line reverts to a simpler pipeline with lower clock rates and 
multiple processor per chip

• Although dynamic power is the primary source of power dissipation

make the transistors too leaky
• To try to address the power problem designers– have already attached large devices (that could be too expensive 
for desktop computers) to increase cooling– turn off parts of the chip that are not used in a given clock cycle
• A variety of design techniques and technology innovations are being 
deployed to control leakage
• But, it is hard to lower voltage further

The Switch from Uniprocessors to Multiprocessors
• Prior to the mid-1980’s, processor performance growth was largely 
technology-driven and averaged about 25% per year
• The increase in growth to about 52% since then is attributable to 
more advanced architectural and organizational ideas
• Since 2002, the performance growth has slowed to less than a 
factor of 20% per year, due to the limits of power, available 
instruction-level parallelism, and long memory latency

The Switch from Uniprocessors to Multiprocessors (cont.)
• Power has replaced die area as the most critical resource of 
microprocessor design
• The power limit has forced a dramatic change in the design of 
microprocessors
• Computer designers chose a different way from the way they designed 
microrprocessors for their first 30 years
• Conserving power while trying to increase performance has forced the 
hardware industry to switch to multicore microprocessors, thereby forcing 
the software industry to switch to programming parallel hardware
• A multicore microprocessor: A microprocessor containing multiple 
processors (cores) in a single integrated circuit– a processor is referred to as a core– a microprocessor is referred to as a multicore microprocessor– e.g., a quadcore microprocessor chip contains 4 processors (or cores)
• As of 2006, all microprocessors have multiple processors per chip
• The official plan of record for many companies is to double the number of 
cores per microprocessor per semiconductor technology generation, 
which is about every two years

The Switch from Uniprocessors to Multiprocessors (cont.)
• The benefit of switching to multicore microprocessors is often on 
throughput rather than on response time
• To get significant improvement in response time, programmers 
need to rewrite their programs to take advantage of multiple cores
• In the past, programmers could rely on innovations in hardware, 
architecture, and compilers to double performance of their 
programs every 18 months without having to change a line of code
• Today, for programmers to get their significant improvement in 
response time, they need to rewrite their programs to take 
advantage of multiple processors
• Moreover, to get benefit of running faster on new microprocessors, 
programmers will have to continue to improve performance of their 
code as the number of cores doubles

Measuring Performance Using Benchmarks
• A computer user who runs the same program day in and day out would be 
the perfect candidate to evaluate a new computer
• There are two ways to measure performance of computer systems:– use programs typical of expected workload:
• the mixture of programs and OS commands that users run on a 
computer most of the time
• is either the actual collection of applications run by a user or 
constructed from real programs to approximate such a mix
• specifies both the programs and the relative frequencies– using benchmarks:
• programs specifically chosen to measure performance of expected 
class of applications
• Hopefully, predict the performance of the actual workload
• There are four levels of benchmarks (in order of decreasing accuracy):– real programs – kernels (small benchmarks)– toy benchmarks (small benchmarks)– synthetic benchmarks

SPEC CPU95 Case Study (cont.)
• At the same clock rate:– Pentium Pro is 1.4 to 1.5 times faster on SPECint95– Pentium Pro is 1.7 to 1.8  times faster on SPECfp95
• Pentium Pro with a slower clock rate has a better performance!
• Pentium Pro performance scales better with increases in clock rate– Increasing clock rate from 150 to 200 MHz on SPECfp95:
• Pentium Pro shows an improvement of 1.24
• Pentium shows a smaller improvement of 1.18
• For both processors, increasing the clock rate by a certain 
factor increases performance by a lower factor (Amdahl’s law!)– Doubling Pentium Pro clock rate from 100 to 200 MHz:
• SPECint95 performance improves by only 1.7
• SPECfp95 performance improves by only 1.4– The reason for this is performance loss in the memory system– Since the speed of the main memory is not increased, increasing 
processor speed increases the bottleneck at the memory system 
• Improvement sources are organization and compiler enhancements

SPEC CPU2000 Case Study (cont.)
• The performance of each of these processors scales almost linearly 
with clock rate increases– This should not be the case, since losses in the memory system 
often worsen with higher clock rates– The strong shown performance is due to:
• The aggressive cache systems used on both processors
• The inability of many of the SPEC benchmarks to stress such 
a memory system
• Pentium 4 is relatively better than Pentium III on floating-point 
benchmarks
• Pentium 4 is relatively worse than Pentium III on integer 
benchmarks
• Pentium 4 provides a set of new instructions that provide a 
significant boost for floating-point

Fallacies and Pitfalls
• Pitfall: expecting the improvement of one aspect of a 
computer to increase overall performance by an amount 
proportional to the size of the improvement
• Fallacy: computers at low utilization use little power
• Pitfall: using a subset of the performance equation as a 
performance metric
